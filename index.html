01

Client work · Built on Wix

Rolling Lawns Farm

A dairy farm in Greenville, Illinois that supplies milk and ice cream to markets and restaurants. The farm wanted the tours it runs at the barn and the Milk House to be easier to find, and the previous site was out of date and did not work on phones. The rebuild reorganised the page around the products and the tours, replaced the content, and made the layout responsive.

02

Personal project · Concept storefront

KINETA

A storefront for a fictional sportswear brand, built to work through a full shopping flow: a catalogue you can filter and sort, product pages with size selection that marks what is out of stock, a cart and wishlist that survive a reload, and a simulated checkout. The catalogue is local data, there is no backend, and no payment is processed.

Live demo (opens in a new tab) Source (opens in a new tab)
Type
Personal project, concept store
Built with
React, TypeScript, Vite, Tailwind, Zustand
Data
28 products from a local file, no backend
Build notes

What it does

  • A 28 product catalogue, filtered by category and size, sorted by price, newest or featured.
  • Product pages with size selection, with sizes that are out of stock shown as unavailable.
  • A cart and a wishlist held in localStorage, so both are still there after a reload.
  • A checkout in three steps, Shipping, Payment and Review, then a confirmation screen.

The checkout validates its fields but takes no payment and sends nothing anywhere. It asks for made up details on purpose.

How it is built

Every page reads products through one repository module, so the catalogue has a single source and swapping it for an API would be a change to that file rather than to the pages. Cart and wishlist state sits in Zustand and is written to localStorage, which is what makes it survive a reload.

Motion and 3D

Two animation libraries with a line between them: GSAP with ScrollTrigger drives anything tied to scroll position, Framer Motion drives anything tied to state, like the cart drawer and the checkout steps. Neither is applied to the same element as the other. One Three.js scene renders a shoe and is code split, so it only downloads on the pages that show it.

On the home page the brand name scales up until it fills the screen. The scale is applied to the text box rather than to its full width wrapper, which keeps the layer the browser has to hold within a size it will rasterise. Measured in Chrome that is the difference between roughly 5,000 pixels across and 34,000.

03

Proposal · Restaurant site

Grouchy's Public House

A six page site for a steakhouse and bar on Main Street in Greenville, built as a proposal rather than commissioned work. It covers the menu, the story, a gallery, visiting details and a table booking flow. The prices and the photography are placeholders until the restaurant supplies its own.

Live demo (opens in a new tab) Source (opens in a new tab)
Type
Proposal, not commissioned
Built with
Astro, TypeScript, Tailwind, GSAP
Status
Demo only, prices and photos pending
Build notes

What it does

  • Six pages: home, menu, about, gallery, visit and a booking flow.
  • A four step table booking, from picking a table through to confirmation. Nothing is sent anywhere.
  • A whiskey glass rendered in 3D beside the booking section.

How it is built

Astro suits a site that is mostly photography and text that does not change, because it ships HTML with no framework attached. GSAP and Three.js are kept out of the initial download and load only on the page that uses them, and the 3D glass only once it is scrolled near.

Nothing starts hidden in the markup. Reveals animate from a start position to where the element already sits, so if the animation library does not load the page still reads normally.

The 3D glass, and when it is skipped

What ships in the HTML is a glass drawn in CSS. The WebGL version loads over it only when the screen is wide, the browser reports WebGL support, and reduced motion is not requested. If any of those is false the CSS glass is what stays on screen, so the section does not depend on WebGL to look finished.

04

Personal project · JavaScript app

Task Dashboard

A task manager that keeps its list in the browser. Each task carries an owner, a due date, a priority, a category and notes, and the whole list can be searched, filtered and sorted. Built with plain JavaScript, no framework and no build step.

Live demo (opens in a new tab) Source (opens in a new tab)
Type
Personal project
Built with
HTML, CSS, JavaScript
Storage
localStorage, no backend
Build notes

What it does

  • Search that covers the task, the owner, the category and the notes at once.
  • Filter by status and priority, sort by date, priority or name.
  • Counters and a progress bar that follow the list as it changes.
  • A button that opens a task in Google Calendar or Outlook as a prefilled event.

How it is built

The tasks live in one array and the list on screen is drawn from it each time something changes. Search, filter and sort are three separate functions that run over that array in turn, so a new filter can be added without touching the other two.

Working out overdue

Overdue is not a value stored on the task. It is worked out from the due date every time the list is drawn, which means a task becomes overdue on its own once the date passes, without anything having to run to update it.
